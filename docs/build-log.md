# Build log

Dated notes of PayPal and sponsor-tool surprises, walls and workarounds.

## Wed Nov 11 2026

- **Payouts in the sandbox:** `POST /v1/payments/payouts` returns `PENDING` at once; items reached `SUCCESS` after 15 to 30 seconds of polling `GET /v1/payments/payouts/{id}`. A payout to an email with no PayPal account settled as `UNCLAIMED` in the same window. The app polls instead of waiting for webhooks.
- **Orders without a browser:** an order created through `@paypal/paypal-server-sdk` with a sandbox test card as `payment_source.card` is created and captured in one call (`COMPLETED`, with the fee breakdown). That let the seed create real money-in without Playwright and the buyer login.
- **Balances lag:** `GET /v1/reporting/balances` carries an `as_of_time` that trails the ledger, so after paying out the reported balance was unchanged for a while. The pay rule therefore subtracts what the current batch is about to send before comparing.
- **Transaction Search lag:** `GET /v1/reporting/transactions` showed zero items for payouts made minutes earlier. The reconciliation panel labels such rows "waiting for Transaction Search" until they are three hours old.
- **Agent Toolkit:** `get_merchant_insights` answers "not supported in sandbox mode". The auditor keeps the tool but reports that answer honestly; `list_transactions` works.
- **APIMatic Context Plugin:** `npx skills add .../plugins/paypal/skills/typescript` installed nine skills into `.agents/skills`. The Server SDK it documents covers Orders but not Payouts, Reporting or Webhooks, so those are plain REST with one shared token helper.
- **Vision check:** `google/gemma-4-31B-it` named all nine seeded room photos correctly in about 1.5 s for the set. The model only reports what it sees; code compares that with the checklist.
- **Text model:** `Qwen/Qwen3.8-27B` sometimes returns empty `content` when `max_tokens` is small (the budget goes to reasoning). Raising the budget fixed it; the fallback model covers the rest.
- **Cancel unclaimed item fails in the sandbox:** `POST /v1/payments/payouts-item/{id}/cancel` answered `BATCH_NOT_COMPLETED` while the batch was still processing, then `500 INTERNAL_SERVICE_ERROR` on every attempt once it was `SUCCESS`, for two different UNCLAIMED items, with and without a body, on both sandbox hosts. The app treats PayPal as the source of truth: it re-reads the item, keeps it UNCLAIMED, shows the debug id on the card and offers "Hold next payout" instead. No success fixture exists for Replay, because none was ever observed.
- **AG Studio 3.0.0 against the 3.1.0 docs:** the docs site is one minor ahead of the boilerplate's pinned version. The Agent Framework API used here (`createAiHarness` with a config builder, `directLlmRunner`, `builtIn`, `tools.delegateTo`, `api.defineAiTool`) exists in 3.0.0; the types in `node_modules/ag-studio/dist/types/api/ai` were the reliable reference.
- **AG Studio AI panel only exists in edit mode:** panel types for view mode are `filters` only, so "Ask the auditor" switches Studio to edit mode and opens the `ai` panel through report state (`panels.ai.collapsed = false`), a moment after the mode change, because Studio re-opens its edit panels when the mode flips.
- **Studio `context` is read once:** custom widgets get the application context, but it is an initial property. The dashboard passes a small store object (`get`, `subscribe`, `reload`) and the widgets read it with `useSyncExternalStore`, so an approved action in a widget updates every other widget and the Studio data sources.
- **Studio height:** `AgStudio` with `height: 100%` fell back to 600 px inside a flex item whose height came from flex-grow. Giving the wrapper an explicit height fixed it.
- **W&B Responses API works with the boilerplate adapter:** streaming, reasoning items and `function_call` events all arrive in the shape the adapter expects, so the proxy route only swaps the base URL and model, retries 5xx and falls back to the second model.
- **Playwright video and device scale:** `recordVideo` with `deviceScaleFactor: 1.5` produced a larger frame with the page in its top left corner, not a sharper page. The compose step crops the phone clip to the real viewport; the desktop clips were recorded at scale 1.
- **Demo clock:** jobs completed in the demo get check-in and completion stamped at submit time, which made two back-to-back demo jobs look like a double booking. Stamped jobs carry `demoClock` and are left out of the overlap rule.

## Thu Nov 12 2026

- **Vercel Blob is not read-your-write through `get`:** on the hosted demo the pay route read an older state than the one the submit route had just saved ("Job is scheduled, not verified"). Measured against the project's store: after overwriting a blob, `get(path, { useCache: false })` kept returning the previous content for two to three seconds, and a path read before it existed could keep answering "not found". `list`, `head` and `put` were consistent at once. Reading from origin alone therefore did not fix it.
- **Fix, part one, storage:** a document is never overwritten on Blob. Each save creates `payday/<key>/v<sequence>.json` with `allowOverwrite: false`; the current document is the highest version `list` reports. Reads are exact (the content of a version never changes), and "create version n+1 only if it does not exist" is an atomic compare-and-swap. A failed read throws; only a document with no versions (and no legacy file) counts as missing. Old versions are deleted every few saves.
- **Fix, part two, flows:** every route used to load the whole state, work, and save the whole state, so a slow request (the status poll) could erase another's result. Now slow work (the model, PayPal) runs on a snapshot and each change is applied to the latest state inside `mutate()`, which retries on a version conflict. Paying reserves the payout and marks the job paid in the same atomic change that checks the rules, before PayPal is called.
- **Tests without the network:** `tests/store.test.ts` swaps in an in-memory backend with a hook that lets a second request write between another request's read and write. It covers the lost update, the stale poll erasing "verified", a failed read not creating a fresh state, and two simultaneous pay requests reserving a job exactly once.
